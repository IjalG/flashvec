# flashvec 验收判据（acceptance protocol）

> [English](../acceptance-protocol.md) | 简体中文

> 这份文档回答一个问题：**一条优化凭什么算「被接受」？**
> 它把「看着快」和「真的快」分开，写清算术口径、可复现性口径与语义口径。
> 数据来源：`bench/ab/`（同进程 A/B 夹具）、`verify/`（第三方位级对拍与结构检查）、`docs/research/raw/`（原始日志）。
> 本文只引用已验证的数字，未测的部分写「待测」。

> **`docs/research/raw/` 是每次 `make run` 覆盖的产物，不是不可变存档。**
> 每次重跑都会重写 `ab_baseline_head.{txt,tsv}`、`_matrix.tsv`、`_smallN.tsv`、`ab_aa_floor.tsv`。
> 实测同一台机器上「可分辨点数」在四次运行里分别是 90 / 92 / 93 / 107（分母 304），
> 全点中位比在 1.0063–1.0079 之间。
> 引用时必须连同时刻一起写：header 行有 label/rev，文件 mtime 就是那一轮的时刻。
> 否则会把两个不同轮次的数字混着引用。
> 需要长期对比的结论请抄进 `docs/research/` 的分析文档，不要依赖 raw 里的文件。

本机：AMD Ryzen 7 5700U，Zen 2，8C/16T。L1d 32 KiB/核，L2 512 KiB/核，
**L3 4 MiB/CCX × 2 CCX = 8 MiB 芯片总量，单线程可见 4 MiB**，行 64 B。AVX2+FMA，无 AVX-512。

---

## 0. 一页版：五条必须同时满足

一条优化要算被接受，必须**同时**满足下面五条。这里的「优化」指新的批量入口、换指令、换归约写法、加 NT store 等改动。

| # | 判据 | 不满足意味着什么 |
|---|---|---|
| 1 | **位级对拍通过**：全形态 × 全尾长 × 三档编译配置，三项各自的定义见 §1 | 数值契约被改动了。逐元素型入口承诺位模式相同，任何一处不同都是契约破坏，不是「浮点噪声」 |
| 2 | **目标规模同进程中位比 ≥ 1.15x** | 在采集它的那个规模上没有可测增益。「同进程」是关键：跨进程/跨运行在这台机器上可差 20–25% |
| 3 | **同向复现**：换测量顺序（AB→BA）或重建二进制后重跑，方向一致且仍 ≥ 1.15x | 单次测量的方向可能是噪声或代码放置的假象，例如对齐、跨 TU 内联变化 |
| 4 | 该 (op, size) 点的 **A/A 地板 < 声称的增益**；A/A 地板 = 两份**完全相同**代码的比值偏差 | 增益小于这台机器对同一份代码的分辨率，无法与测量噪声区分 |
| 5 | **其他规模不回退超过 5%**；预期性回退必须**显式标注**，例如 L2/L3 档的 NT store | 用一个大数组的收益换小数组的普遍变慢，是负优化 |

第 1 条的三项展开如下，逐项定义见 §1。
全形态指三种形态：库内定义、头文件 inline、纯 C 回退。
全尾长指 `n = 0..17` 及若干个非 4/8 倍数的规模。
三档编译配置指默认档、`-O3 -march=native`、`-march=native -mfma -ffp-contract=fast`。

五条之外还有一条方法论，下面 §4 展开：**单点比值不可信**。判据必须建立在**逐规模中位比**与**全点中位比**上，不能用某一个 (op, n) 的单次读数下结论。

自动化入口是 `make -C bench/ab verify OP=<op> N=<规模>`。它一次跑完并打印逐条判定，FAIL 时会说清是哪一条、差多少。细节见 `bench/ab/README.md` §11。

结构层面的配套检查是 `bash verify/checks.sh`。查的内容是头文件纯净度、派发位置、禁用内建名、产物级指令普查、已废弃内部名不得复活。

## 1. R1 位级对拍：为什么必须是「全形态 × 全尾长 × 三档」

- **全形态**：同一份实现在三种形态下必须给同一个结果。三种形态指库内 `extern` 定义（`FV_USE_EXTERN` / `FV_BUILD`）、
  头文件 `static inline`（默认）、纯 C 回退（`-DFV_I_NO_INTRINSICS`，走标量）。形态差别会改变内联与指令选择，FMA 收缩最容易在这里出现。
- **全尾长**：主循环是 `n/4`、`n/8`（vec4 是 `n/2`），尾巴走标量。`n = 0..17` 覆盖所有余数。
  另外要测 `n` 略大于批量整数倍的边界，以及 `n = 0`、`ptr = NULL`。
- **三档编译配置**：默认档（`-O3 -fno-math-errno -ffp-contract=off`）、`-O3 -march=native`，
  以及最严的 **`-march=native -mfma -ffp-contract=fast`**，即消费者自己带 FMA 选项。

  头文件用 `#pragma GCC optimize("fp-contract=off")` 守住有收缩风险的入口。这一档就是那条 pragma 的唯一证据：少了它，`vfmadd` 会静默出现。

判等口径：IEEE 位模式 `memcmp`。唯一例外是**两侧都是 NaN** 时判相等并单独计数，payload 可以不同。±0.0 的差异按位如实判不一致。

每个输出缓冲区都要有越界写 canary，即 `o[n..)` 不许被写。`_idx` 变体还要检查「未被 idx 引用的 `o[i]` 没有被改写」。

**唯一豁免：`dot_soa`，含 vec3/vec4 版本**。它用 4 个累加器加末端一次归约来打断依赖链，归约顺序与逐元素路径不同，所以不做位级判定，只统计误差。它的**契约必须写清**，见 §5。

## 2. R2/R3 比值与复现：为什么要换顺序、换二进制

- **同进程**：A 与 B 必须在同一个进程里交替跑（A/B/A/B…）。否则频率迁移、外部负载、页分配差异会混进比值。本机变频 1.64–3.97 GHz，同一份代码跨运行可差 20–25%。
- **换顺序（AB → BA）**：抵消「后跑的那个受 cache/频率恢复之利」这类系统性偏差。
- **换二进制**：同一份源码只改代码放置（`-falign-functions=64 -falign-loops=32 -falign-jumps=32`），语义零变化。这一条专门排除「代码放置」这类一次性因素。
  实测它能给 L1/L2 档带来 5–10% 的差别，而那不是优化。

---

## 3. R4 A/A 地板：这台机器到底能分辨多小的差别

A/A 地板是**两份完全相同代码**在同一进程、同一规模下交替跑出来的比值偏差，理想值 1.000。它给出这台机器对「同一份代码」的分辨率下限。
任何「候选快 r 倍」的结论，只有 **(r − 1) > floor_dev** 才可能为真。

本机一组实测，数据取自**某一轮**的 `docs/research/raw/ab_aa_floor.tsv`，304 个大 N 测量点，warm + cold：

- `floor_dev = |ratio − 1|` 的分布：**29/304 个点 ≥ 15%**，**17/304 个点 ≥ 20%**。
- 最坏点是 0.583，出现在 `add_x4` @ 131072 的 warm 档。只看「可分辨」的点，最高 0.312。
- 也就是说，**15–20% 的地板在这台机器上是常态，极端点还要更差**。声称 1.15x 的优化在没有 A/A 地板的点上无法与噪声区分。

> 上面这几个数是 29 / 17 / 最坏点 0.583。它们和 §4 的可分辨点数一样，都是**某一轮** raw 的读数，
> 不是常量。同一台机器、同一份代码重跑，可分辨点数在 90 / 92 / 93 / 107 之间漂移，分母恒为 304，
> 见 §4 与文首的 raw 漂移说明。**结论不依赖具体是哪一轮**：
> 「地板常态 15–20%，单点因而不可判」这个判断在四次读数里都成立。

配套的两条读数规则：

1. **`resolvable = 0` 的点不要用来判**。这一档的配对 IQR ≥ 5%，外部负载已经污染了它。
2. **优先看 L1/L2 档**：L3 与 DRAM 档的取样变异系数常超 5%，能被外部负载污染。

## 4. 为什么单点比值不可信

这台机器是共享机，loadavg 4–9 / 16 核，L3 与 DRAM 档的取样变异系数常超 5%。一组实测：
可分辨点数约 **30–35%**，四次运行分别是 90 / 92 / 93 / 107，分母恒为 304。

这个数随运行漂移，引用请带轮次。「可分辨」的口径是配对 IQR < 5.0%，分母 304 就是大 N 测量点数。
同一行还会单独报出 cold 档不达标的一批点，见 `docs/research/raw/ab_baseline_head.txt` 的「取样稳定性」一行。

**四次读数是四次 `make run`，raw 里只留下最后一轮**。早期轮次的具体数字只能从本表的记录里读到，这也是引用 raw 时必须带时刻的原因。

所以：

- 判据用**逐规模中位比**，即每个规模 n 一个比值、取中位；也用**全点中位比**，即整条扫描线的中位。
- 单个 (op, n) 的一次读数只能用来**发问**，不能用来下结论。
- 报数字时必须同时报四件事：工作集大小、缓存层级、编译选项、是否可分辨（CoV / 配对 IQR）。只报一个「加速比」的数字没有意义。

## 5. 语义验收：分段不变性（split invariance）

这类性质测试套件不会自动覆盖，但调用方一定会遇到：分块并行、流式处理、按 chunk 累加。

**逐元素型批量入口具备分段不变性**：`add / sub / scale / lerp / madd / len / normalize` 及其 `_x4` / `_soa` / `_mask` /
`_idx` 变体。同一数组切成任意多段分别调用，输出与一次调用**逐位相同**。

**归约型入口不具备**：`fv_vec2_dot_soa` / `fv_vec3_dot_soa` / `fv_vec4_dot_soa` 的归约树随切分改变。同一份输入的实测：

| 用例 | 整段一次调用 | 切 2 段分别调用再相加 | 相对差 |
|---|---|---|---|
| `fv_vec2_dot_soa`，n = 1000 | −64.4546509 | −64.4543991 | **≈3.9e-6** |
| `fv_vec2_dot_soa`，n = 8192 | 79.6643372 | 79.6624146 | **≈2.4e-5** |
| 对照组 `fv_vec2_add_x4`（同语料、同切分） | — | — | **逐位一致** |

覆盖 12 组语料：`dot_soa` **12/12 全部不一致**，`add_x4` **12/12 逐位一致**。后一条是对照组，证明实验有效。

结论与要求：

- 这是归约的**设计必然，不是缺陷**：归约顺序改变必然改变舍入。
- 但它**必须写进契约**，否则调用方会以为是浮点噪声。需要「结果与切分无关」的调用方必须用标量 `fv_vec2_dot` 顺序累加，或自己固定切分方式。
- 幅度不小：2.4e-5 约是「n ≤ 1000 相对误差 ≤ 4e-8」的 400 倍。这两个说法讲的是**两件事**。「与标量路径的差」是头文件里那个误差数字，「与另一种切分的差」是本节。前者不能当后者的上界。
- 因此**接受一条优化时，`dot_soa` 的位级豁免不等于精度豁免**。它的误差必须按「语料条件 + 绝对误差」报，不能只给一个裸的相对误差，更要说明「分段调用会变」。

## 6. 字节账：名义流量 vs 含 RFO 的真实流量

GB/s 用**名义**字节（读 + 写）算会把 `_stream` 的 NT store 收益看错。普通 store 在写 miss 时要把整条 cache line **先读进来**，
这一步叫 RFO，read-for-ownership。真实流量是「写一次 + 读一次」。

| 入口 | 名义 B/元素 | 真实 B/元素 | 说明 |
|---|---|---|---|
| `add_x4` / `sub_x4` / `lerp_x4` / `madd_x4` / `add_soa` | 24（16 读 + 8 写） | **≈32**（+8 RFO） | 输出数组被多读一遍 |
| `scale_x4` / `scale_soa` | 16（8 读 + 8 写） | ≈24（+8 RFO） | 同上，少一路读 |
| `dot_soa`（vec2/vec3/vec4） | **16**（ax/ay/bx/by 四条 `float` 数组 × 4 B） | 16（纯读，不写即无 RFO） | **不是 32 B**：每元素只读 4 个 float |
| `normalize_soa` | **16**（8 读 + 8 写） | ≈24（+8 RFO） | **不是 16+16** |
| `*_stream`（NT store） | 24（与普通版相同） | **24**（无 RFO） | 真实收益是**少走 25% 的字节**，不是每字节更快 |

两条判据：

1. 同一算子的普通版与 `_stream` 版，**真实** GB/s 应基本相等，两者都顶在 DRAM 带宽上，而**名义** GB/s 差 1.33 倍。
   若名义与真实都差 1.33 倍，说明增益不是流量带来的。这是识别假阳性的一把尺子。
2. NT store 只在**工作集远超 L3、写流是干净的一次性写**时才有这 25% 的字节。工作集落在 L2/L3 里时，
   它比普通版慢 **2–8 倍**：L2 内实测 **0.13–0.51x**，6 个入口全部判 FAIL(变慢)，见 §9 第 2 条。

这也是**拐点**必须用真实流量再算一遍的原因。`add` 名义 24 B/元素对应 4 MiB ÷ 24 B ≈ 1.75×10⁵ 元素。按真实 32 B/元素算，拐点还要更早，约 1.3×10⁵。

## 7. 缓存口径（报数字的前置条件）

本机 L3 是 **4 MiB/CCX × 2 CCX = 8 MiB 芯片总量**。
`/sys/devices/system/cpu/cpu0/cache/index3` 报 `level=3, size=4096K, shared_cpu_list=0-7`。
**单线程只吃得到自己那 4 MiB**。

- 说「L3 8 MiB 共享」是错的：8 MiB 是芯片总量，不是单线程可用量。
- 拐点按 4 MiB 算：`1.75×10⁵` 个活跃元素 @ 24 B/元素。旧文档按 8 MiB 算成 `3×10⁵`，高了一倍。
- 有直接实测：同进程 A/B 夹具在 **2^17（工作集 3 MB）是 38–57 GB/s**，**2^18（6 MB）掉到 5.6–8.8 GB/s**，断崖正好压在这条线上。
- 本仓库的一致性检查每次都会打印 `index3` 的实测值，也就是 `bash verify/checks.sh` 的 [7] 段，以免文档与机器再次漂移。

## 8. 哪些地方没有可信数据（不要当数字引用）

- **三维 / 四维相对标量的绝对加速比**：现在由 `make bench-vec34` 实测（同进程 A/B、11 轮配对、同轮 A/A 地板；表格见 README 与实施日志）。引用时带上 harness 与工作集；它是测量夹具的结果，不是 §0 的五条验收。
- **AoS↔SoA 拆装成本**：现在由 `make bench-pack` 实测：往返在 **n=8192 约 0.28–0.32 ns/元素**，**n=1M 约 4.2–4.4 ns/元素**（后者受 DRAM 限制）。由此得到判断规则：调用方数据是 AoS 时，`pack + fv_vec2_add_soa + unpack` 在 8192 比 `fv_vec2_add_x4` **慢 2.5 倍**、在 1M **慢 3.1 倍**，因为拆装是纯额外流量；换成效费较高的运算，在数据驻留 cache 时结论反转（8192 档 `pack + normalize_soa + unpack` 比逐元素 normalize **快 3.9 倍**），但 1M 档额外流量让它 **慢 2.3 倍**。实用结论：SoA 入口在“数据本来就是 SoA”，或“数据驻留 cache 且运算足够贵”时才划算；对便宜的运算 + AoS 输入不是即插即用的收益。
- **非 AVX2 硬件上的标量回退**：这是硬件可得性限制，不是库的待办。本机有 AVX2，无法强制 `__builtin_cpu_supports("avx2") == 0`；源码级路径由 `-DFV_I_NO_INTRINSICS` 覆盖，结构性证据是 `verify/checks.sh` 的 [9] 段（基线档里内核仍在、派发走 `__cpu_model` 的 avx2 位）。真实非 AVX2 机器上仍未运行过。

## 9. 走不通的路（留档：别再重做）

这一节记的是**已被实测否决**的方向。它不是「还没试」，而是「试过了，结论是否定的」。重做之前先读这里，并给出「这次为什么不一样」的物理理由。说不出理由就不要重跑，重跑只会得到又一个噪声读数。每条都带证据位置。

第 8 条是唯一一条被实测**接受**而不是否决的。它留在这一节的理由与其余各条相同：别重做，也别从它身上多拿。

1. **`_mask_inplace` 的就地写没有吞吐收益，全档 INCONCLUSIVE**。5 种密度（1% / 5% / 20% / 50% / 95%）× 4 档规模 = 20 个点，
   增益 **-0.10…+0.00**，同轮 A/A 地板 **1.06–1.56**。

   campaign 判定表里它的 4 个规模点也全是 INCONCLUSIVE：4M 档增益 -0.41、地板 1.48。**原因在流量账上**。
   就地写的目标数组本来就要先读后写，对应的 cache line 已在 cache 里，普通 store 在这种情形下**不产生 RFO**。

   「就地」省掉的是 **0 B**，不是 8 B/元素。所以它的价值是**形态**，即省一块输出缓冲、少一次分配，不是速度；不要用它换吞吐。
   证据：`docs/research/raw/ab_campaign_verdict.txt`、`bench/ab/README.md` §10.8。

2. **NT store 在 L2/L3 内是 0.13–0.51x，慢 2–8 倍**。

   `_stream` 的 6 个入口在 n=8192 实测，此时工作集 128–192 KiB，落在 L2 内：
   `add` 0.217 / `sub` 0.301 / `scale` 0.130 / `add_soa` 0.229 / `scale_soa` 0.138 / `normalize_soa` 0.506，
   **6/6 判 FAIL(变慢)**。它只在工作集**远超 L3**、且写流是干净的一次性写时才有那 25% 的字节，见 §6。

   并且必须由调用方**显式选择**，库永不自动切换。反过来也不是「L3 之外总有效」：1M/8M 档 PASS（1.29–1.58x），4M 档 6/6
   INCONCLUSIVE（地板 > 15%），n=131072 是黑名单档。证据：同 §1 与 `include/flashvec.h` 的 `_stream` 契约。

3. **VMASKMOVPS（`maskload` / `maskstore`）在 Zen 2 上是微码级慢指令，这条路已从库里删掉**。
   两个内部名 `fv_i_maskload_add4_avx2` / `fv_i_maskstore_add4_avx2` 标为**已废弃**。

   `bash verify/checks.sh` 的第 [11] 条规则要求它们在整仓出现 **0 次**，复活会当场被门禁拦下。与数字无关的那条理由更重要。
   用它们，「未命中 lane 是否被物理写」会变成**随掩码密度变化**的性质，没有调用方能依赖一个随输入分布变化的存储保证。

   早期探针的数量级是同密度下比整条 `storeu` 慢 1.2–3.8x，本轮**未复测**，只按量级读。证据：`verify/checks.sh` [11]、`include/flashvec.h` 契约。

4. **分段不变性（split invariance）在归约型入口上不成立**。这是设计必然，不是缺陷，但**必须写进契约**：
   `fv_vec2_dot_soa` / `fv_vec3_dot_soa` / `fv_vec4_dot_soa` 的归约树随切分改变。

   n=8192 时「整段 vs 切两段再相加」相对差 **2.4e-5**，n=1000 约 **3.9e-6**，12/12 全部不一致。对照组的 `add_x4` 在同语料上 12/12 逐位一致。
   需要「结果与切分无关」的调用方必须用标量 `fv_vec2_dot` 顺序累加。

   证据：§5 的表、`include/flashvec.h` 的契约。

5. **「内联形态」本身不等于更快**。把实现从「库内定义」换成「头文件内联」只改代码放置，算法零变化。
   本轮以 intra 模式测了 13 个三维/四维入口 × 5 档规模 = 65 个点，intra 模式指 A/B 只差这一个变量。
   结果是 **5 PASS / 8 FAIL(变慢) / 52 INCONCLUSIVE**。

   就在最小的一档 n=8192 里，**同一份源码**的读数从 **0.97 到 1.93** 全都有。0.97 读成慢 3%，说明「内联也能被读成变慢」；
   1.93 读成快 93%，说明「只换形态也能读出接近 2 倍的假增益」。

   同一现象的另一面是同轮 A/A 地板：4M 档那份**完全相同**的代码，两侧比值能到 **1.34–1.61**，即只换目标文件布局就能读出 1.5 量级。
   所以任何「因为内联所以更快」的结论都必须过 R3（同向复现）与 R4（同轮 A/A 地板）。单点比值只能用来发问，不能当证据。

   证据：`docs/research/raw/ab_campaign_verdict.txt` 的 intra 行。

6. **`_idx` 软件预取无效**。实测配置是三种下标分布 × 三档规模 {65536, 1M, 8M} × 三个预取距离 {4, 8, 16} × 两种 hint {T0, NTA}。
   **随机分布 0 PASS / 30 点全 INCONCLUSIVE**，来自夹具，完整表 30 行。

   **三分布合计 0 PASS / 2 个可分辨的变慢 / 52 个 INCONCLUSIVE**，来自自建的同进程 A/B 驱动，54 行。
   R1 位级对拍 8/8 通过：宏开 × 四形态 × 两种 hint，175 296 字节主输出流逐字节相同。**预取没改语义，纯粹没有性能**。

   能分辨的点指配对 IQR < 5%、同轮地板 ≤ 15%，这些点的实际读数如下。
   - 8M **随机**档是最延迟受限的一档，增益 **+0.3% … +1.9%**，也有 -1.8%；同轮地板 1.5%–4.6%。D=4/8/16 与 T0/NTA 之间没有可分辨差别。
   - 65536 **有序递增** 是 **0.606x**，**分块聚类**是 **0.700x**，后者每 64 个下标聚在一个 4 KB 窗口。
     这等于回退 39% / 30%，是 R5 判据（>5% 就不接受）的 6–8 倍，且 R3 同向，来自 D=8 与 D=16 两次独立构建。

     `_MM_HINT_NTA` 在 65536 更差：**0.12–0.41x**。
   - 65536 随机档看着有 1.11–1.24 的「增益」，但**同轮 A/A 地板本身就是 1.48–1.93**。
     三次重复的 ratio 是 1.115 / 1.150 / 1.157，地板 p90 偏差 0.48 / 0.93 / 0.57。那一档是这台机器最难判的点之一，按 R4 必须判 INCONCLUSIVE。

   **原因是从数据里读出来的**：
   - 随机分布下瓶颈不是「提前量不够」，而是**未完成 miss 的并行度**。8M 档每元素 55–60 ns，即 20 B/元素 ≈ 0.34 GB/s ≈ 一个 DRAM 延迟 ÷ 1.5 个并发。
     预取项与需求缺失抢的是同一批 miss 槽位，也就是 L1 fill buffer。

     它把同一批访问**提前**发出，却不增加并行度，所以增益为零。这也解释了为什么扫距离与 hint 都扫不出东西：换提前量不改变槽位数。
   - 有序/分块分布下工作集在 L1/L2 里，硬件预取器本来就覆盖。此时循环是**发射受限**而不是延迟受限，每元素多 1–2 条 prefetch µop 直接换成 25–40% 的吞吐损失。
     NTA 更糟：「非临时」通路对**反复使用**的行是有害的，行留在 L1 里，却被降级或挤掉。
   - 于是这条路的物理上限是「把 latency-bound 变成 MLP-bound」的那一段，而这一段已经被 OoO 窗口拿走了，实测 MLP ≈ 1.5–2。
     再往上只能改**数据布局**，即先把下标分批/排序再顺序访问，也就是调用方做 gather 的预处理。那不是批量入口能做的事。

   证据与复现。夹具是 `bench/ab`：A 取同一棵树的 `FV_I_IDX_PREFETCH=0`，B 取同一棵树的 `=1`。
   用 `bench/ab/mkrename.sh` 加同一份 `ab_variant.cpp` 编出 `var_a.o` 与 `var_b.o` 复用驱动，带 `--aa-each-round`。

   数据在三个文件里：
   - `bench/ab/build/idxpf/sweep_random.tsv`，30 点。
   - `bench/ab/build/idxpf/chk_{1,2,3}.tsv`，65536 随机档三次重复。
   - `pf_D8T0_fv_vec2_{add,scale}_x4_idx.tsv`，粗筛那一对。

   三分布那 54 点用的一次性驱动已随实现一起删除。该驱动是两份 `tests/idxpf_side.c` 包装 TU 加 `tests/idxpf_dist.c`，走 ABBA 方案并每轮同构 A/A。

   数据留在 `bench/ab/build/idxpf/dist/dist_sweep.tsv` 与 `dist/run_{8_0,16_0,8_1}.log`。

   实现也**已整体删除**：`FV_I_IDX_PREFETCH` / `FV_I_IDX_PF_DIST` / `FV_I_IDX_PF_HINT` 三个宏，加两个 `_idx` 循环里的预取分支。
   头文件恢复原状，`grep -c IDX_PREFETCH include/flashvec.h` = 0。

   复核 `make test-header` / `make test-inline` / `bash verify/checks.sh`，11 条规则 FAIL=0。

7. **`-ffast-math` 拿不到任何收益，反而损失精度，并让一个入口变慢。**

   这个库在它的负载上已经贴着硬件极限，fast-math 没有可压榨的东西。实测方式：两个共享库同时加载进一个进程、交替计时，取 7 次中位数，5 个入口 × 4 档规模：

   | 入口 | 规模 | 默认 | `-ffast-math` | 比值 |
   |---|---|---|---|---|
   | `add_x4`、`scale_x4`、`dot_soa`、`len_soa` | 全部 | — | — | 1.00 ± 0.05，即噪声 |
   | `normalize_soa` | 8192 | 0.35 ns/元素 | 0.42 ns/元素 | **0.83–0.85x**，四轮稳定复现 |
   | 所有入口 | 8M | — | — | ≈1.00，受 DRAM 带宽限制 |

   原因在指令普查里。fast-math 把每一条 `vdivps` 换成 `vrcpps` 加一步牛顿迭代：

       default       vdivps=5  vrcpps=0  vrsqrtps=0
       -ffast-math   vdivps=0  vrcpps=5  vrsqrtps=2
       两者          vfmadd=0                    （pragma 那道防线仍然有效）

   `normalize` 的 8 条 lane 互相独立，`vdivps` 的吞吐早就在流水线里摊平了。用三到四条指令换一条除法，只多占发射槽，不缩短依赖链。

   精度，2^20 个随机向量：

   | 入口 | 位模式不同的元素 | 最大相对误差 |
   |---|---|---|
   | `len_soa` | 0 / 1048576 | 0 |
   | `normalize_soa` | 340525 / 1048576（32.5%） | 2.8e-7 |
   | `dot_soa` | — | 1.1e-7 |

   复现：

       c++ -std=c++17 -O3 -fno-math-errno -ffp-contract=off -fPIC -shared -Iinclude \
           src/flashvec.cpp src/flashvec_batch.cpp src/flashvec_vec4.cpp -o /tmp/libbase.so
       c++ -std=c++17 -O3 -ffast-math               -fPIC -shared -Iinclude \
           src/flashvec.cpp src/flashvec_batch.cpp src/flashvec_vec4.cpp -o /tmp/libfast.so
       objdump -d /tmp/libbase.so | grep -c vrcpps   # 0
       objdump -d /tmp/libfast.so | grep -c vrcpps   # 5

   然后用 `dlopen` 同时加载两者、交替计时。这正是消费者会遇到的场景：批量入口是 `static inline`，定义 `-ffast-math` 就是把它用在头文件的实现上。

8. **融合（fusion）——把几趟遍历并成一趟——是这一节里被实测接受的那一条，记在这里的理由与其余各条相同：
   别重做，也别从它身上多拿。** 它只在工作集超过缓存时收益最大，而随它一起到手的那条上限才是最容易丢掉的部分。

   实测：`normalize(a*s + b)` 写成三次调用是 **80 B/元素**（三趟）；融合入口是 **32 B/元素**（一趟，含 RFO）。
   n=1M 时比值 **2.43–2.55x**，n=8M 时 **2.53–2.63x**。再叠 NT store 连输出的 RFO 一起去掉，到 **4.18x** 与 **3.98x**。

   **它不改变逐位语义，所以不需要新的误差分析。** float 的 store 再 reload 是精确的：中间值不会经过更宽的寄存器，
   融合版的输出与三次调用 `memcmp` 完全相同。验收判据因此就是「与分步调用逐位一致」，R1 原样覆盖它。
   `tests/test_madd_norm.cpp` 做的就是这条对拍。

   限制是结构性的：**只有逐元素运算可以这样融合。** 带归约的（`dot`）不行——改变求值顺序就改变结果，
   也就是上面第 4 条。所谓「融合的 `dot`」会是一个带着自己误差分析的新算法，而不是两次调用的融合。

   证据：`include/flashvec.h` 里 `fv_vec2_madd_normalize_soa` 与积分器一组的契约块、
   `tests/test_madd_norm.cpp`，以及 §6 的 80 → 32 那笔账。

**用法**：如果新方案与上面某条同构，先说明「流量账 / 微架构 / 语义」哪一层的假设变了。说不出来就回到 §0 的五条判据，按「先建夹具、再动手」的路子做。
`bench/ab` 里的这条负结果（§1）就是夹具先行抓出来的。

## 10. 已知局限（现行判据的偏差方向，未修）

§9 记的是「试过并被否决的方案」，这一节记的是**判据本身的问题**。它们没有被修掉，所以每一条都限定了上面的 PASS 到底能证明什么。
判据实现见 `bench/ab/README.md`：§10.7 逐规模判据、§11 验收判据、§13 作者自列的六个漏洞。

- **档级判据偏松（已知、未修）**。自检的档级规则用「该档全部点的中位比」去比「单点 A/A 地板的 p90」，也就是 `|该档中位比 − 1| ≤ 该档地板 p90`。
  15 个点的中位数标准误约为单点的 1/√15，即 ≈1/4。

  `bench/ab/ab_bench.cpp` 的注释自己写的就是「15 个样本的中位数，标准误约等于单点噪声的 1/4」。
  所以这条规则会放过比真实档级噪声更大的偏离：拿一个「已经平均掉大部分噪声的数」去比一把「按单次读数定刻度」的尺子，方向必然是松的。未按 √N 收紧的理由：收紧需要一个关于**点间独立性**的额外假设。

  15 个算子的噪声并非独立同分布，它们共享同一段频率漂移与同一批外部负载。而档级规则只是**健康检查**，不是证据，真正的判据是逐点的 R2/R3/R4。
  **不要把「档级 PASS」当成「这个优化有效」的证据。**
- **A/A 地板只度量 A 侧的噪声**，即 A vs A，而 A/B 比值的噪声还含 B 侧。两侧噪声不同时地板会低估抖动。也就是说地板是**下界**：地板小不等于这个点可判，只等于「A 侧自己跟自己」能分辨。
- **INTRA 模式的地板用参照 op 打**，即 ref vs ref，不是 new vs new，存在「用一个 op 的噪声代表另一个 op」的问题。
  新入口与参照 op 的访存形态、尾巴长度、寄存器压力都可能不同，地板的量级不能假设可以搬过去。
- **档级地板本身在轮次之间会翻倍**。实测 65536 档是 0.130 / 0.169 / 0.218。同一档能在「可判」与「INCONCLUSIVE」之间翻转。

  现行 raw 留下的那一轮里，n=65536 warm 的地板就是 **0.218**，已经触发「地板 > 20% → 该档 INCONCLUSIVE」的兜底，而同一个档在另两轮只有 0.130 / 0.169。
  所以只有「**逐点 PASS 且该点地板小**」才算硬结论。

  「整档 PASS」在下一轮重跑里就可能变成 INCONCLUSIVE，它描述的是一次测量，不是一个性质。

一句话：上面四条都在说同一件事。**档级/汇总层面的 PASS 是夹具在做健康检查，逐点的 R2/R3/R4 才是证据。** 任何「因为整档 PASS，所以这个优化有效」的推论都在这条边界之外。
